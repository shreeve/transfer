# Handoff

How the code works now, why it is built this way, and the traps that already cost a day. `docs/SPEC.md` is what the product does; `AGENTS.md` is the rule list; `docs/RELEASING.md` is releases and updates. The package builds on Apple-silicon macOS 27 with the Xcode 27 toolchain with no warnings, and `swift test` passes.

## The seam

Two protocols in `TransferCore` are the seam (`RemoteSession.swift`). `SessionProvider` is the library: saved servers, one `RemoteSession` per server, the config, and `transfer(_:progress:)`, which runs every paste and drop. `RemoteSession` is one server. `TransferHub` and `SSHConnection` in TransferIO implement them. Every window and tab has its own `TransferModel`, which asks the hub for sessions, so windows share one login per saved server. The model holds the server it shows as one `ServerContext`, made when a connect starts and installed whole once the login works; work for a server counts only while its context is installed, so a slow listing or a late login never lands in a window that has moved on. Work the user starts takes the context before its first await and keeps it: a star, a paste, or a navigation acts on the server it began on, and Upload…, Download Copy…, or a paste between servers whose window has moved on meanwhile does nothing and says so. A window that closes calls `close()` on its model, which stops its listings, its login, and its sheets at once; its queued transfers run on.

The library root is `~/Library/Application Support/Transfer`, or the folder `TRANSFER_LIBRARY` names (`LibraryOverride`). Under it: `transfer.sqlite`, `config.json`, `Live/`, `ssh/` (control sockets), and per-login scratch. One copy of Transfer holds a library at a time: the hub takes an exclusive `flock` on `transfer.lock` for its life, and a second copy is refused, since the launch sweeps, the temps, and the control sockets all assume no other process is using the library. Caches go to `~/Library/Caches/Transfer` (previews) and `~/Library/Caches/com.github.shreeve.transfer` (the clipboard's staging), or both to `Caches/` under a custom root, so tests and development builds never touch the user's.

## The SSH session

`SSHConnection.swift` is login, host keys, askpass, and channels; `SSHConnection+Transfers.swift` is the transfer engine; `SSHConnection+Tar.swift` streams a folder download's small files with the server's `tar`; `Subprocess.swift` runs every helper process.

- **Login** is single-flight: a `connect` while one is in flight joins it, but a login already stopping is waited out and a fresh one starts. A login stops when the last caller waiting for it leaves, or when a caller still waiting answers one of its questions with Cancel. Its questions go to the caller that joined last and still waits (`LoginPrompts`); a question taken back from a caller that left goes to the next. The master is `ssh -N` with `ControlMaster=yes`, `ControlPersist=no`, `ForkAfterAuthentication=no`, `Compression=no`, `ServerAliveInterval=15` and `ServerAliveCountMax=3` (a dead network is noticed in about 45 s), and `StrictHostKeyChecking=yes`. Every ssh that joins or runs on the server also passes `RemoteCommand=none`, `RequestTTY=no`, `ClearAllForwardings=yes`, and `PermitLocalCommand=no`, since `~/.ssh/config` may set any of them for the user's own logins, and a `ControlPersist` would fork the master away where the app cannot stop it. A five-minute limit covers the login, password prompts included; a host-key question has none, and the master's retry after it gets five minutes of its own. A login dropped before authentication (sshd's `MaxStartups` or `PerSourcePenalties`) is tried twice more. Everything a login starts is released together, and a new login waits until the previous master has exited, so an old master never unlinks a socket a new one has bound. A session that replaces another for the same server (its settings changed) starts the old one's disconnect and its first login waits for it (`init(replacing:)`), since ssh removes the control socket by name. The old one, which a window may still hold, never logs in again (nor does a removed server's): its `connect` fails with `retiredError`.
- **Host keys:** ssh checks the key itself, against the user's own files, so a known host costs one connection. Only when ssh refuses the key (`HostKeyFailure` reads its stderr) does a probe learn the offered key: a no-auth `ssh … true` into a temporary known-hosts file under `hostkey-*`, which honors `~/.ssh/config`, aliases, and `ProxyJump`. The user sees First Seen or Changed, as ssh judged it, and the master starts once more, so a first contact is three connections. Always Trust and Replace write only the first user file `ssh -G` names, hashed when `HashKnownHosts` is on, in one `O_APPEND` write; Replace first removes the old lines with `ssh-keygen -R`. Trust Once hands the master the probe's file until disconnect. Cancel on a first-seen key ends the login as `.cancelled`; declining a changed key is `hostKeyRejected`, as is a `@revoked` key, which is refused without a question. When `ssh -G` failed, Always Trust and Replace fail with an error rather than trust for one login; a config whose known-hosts file is `/dev/null` gets trust for this login only, with a notice.
- **Askpass:** each login gets an `ask-*` folder under the library root with a helper script; ssh runs it for each prompt, and the model shows a sheet. The helper gives up with the login or as soon as its folder is removed, and lets go of ssh's stderr at once; `Subprocess` waits at most a second for a process's pipes after it exits, so a Cancel during the host-key probe ends the login at once. A password and a key passphrase are separate Keychain items (`KeychainStore.Kind`), so a passphrase is never sent as a password; each answers only this server's own prompt of its kind, never a `ProxyJump` host's, and only once per login. Disconnect and every failed login remove the login's `ask-*` and `hostkey-*`; the hub removes every `ask-*`, `hostkey-*`, and 0.1.7's `key-*` when it starts, holding the library lock, so none belongs to a login in progress.
- **Channels:** SFTP is spoken by this app on passengers, `ssh -S sock -s -- <host> sftp` with `ControlMaster=no`, `BatchMode=yes`, and `ProxyCommand=/usr/bin/false`, so a passenger whose master is gone or refuses it fails at once instead of logging in on its own with the default port and keys. Browse, interactive, and walker open at login; a reserved one that dies is reopened when next needed, at most once every 5 s. Data channels open on demand, at most seven (`SSHConnection.dataChannels`: three reserved plus seven is sshd's default `MaxSessions` of 10), and after the server refuses one, no other opens for 10 s; then the first caller waiting opens one (and goes to the back of the line if it is refused again), so a copy's pool grows back. A channel gives up when SFTP has not started within 15 s (a shell startup file that prints text fails at once with a clear error), and when a server has answered nothing for 60 s while requests wait; `copy-data`, which answers only when the whole file is written, is exempt. When the master dies, every waiter gets a lost connection, which transfers retry, and the window hears `.disconnected`.
- **The data pool** shares channels (`SSHConnection.DataShare`): a file of at most 256 KB takes a sixteenth of one, a larger file or one of unknown size takes it whole. A caller takes an idle channel, else opens one while fewer than seven are open or opening, else the least loaded with room; waiters are served in order, so a large file first in line is not passed by small ones, nor by a newcomer opening a channel after a refusal's backoff. Sixteen per channel keeps at most 112 files open on the Mac and 32 handles on each `sftp-server`.
- **The interactive lane** (`InteractiveLane`) runs the file the user is waiting on, one job at a time. Kinds: `.preview` (Quick Look, inspector, prefetch), `.view` (a file opened to view), `.open` (a Live download), `.save` (a Live upload). Each starts on the interactive channel, not the data pool, so it never queues behind a folder copy. Opens, views, and saves run in order and are never interrupted; previews wait behind them, and only a newer preview replaces a preview.
- **Listing** ends at the first end-of-folder status, dropping the pages still asked for (pages are taken in the order asked and a handle's requests are answered in order, so they end it too; waiting for them was a round trip on every listing); an empty page does not end it, and 64 empty pages in a row fail it, and keeps four `READDIR` requests in flight, sixteen once a folder has filled four pages, and streams pages. `SFTPChannel.readDirectory` drops every name that is not exactly one path component, and `SFTPWire` refuses a frame of length zero or over OpenSSH's own limit, and checks every field's length against its packet.
- **Renames** the user asks for never replace: `SFTPChannel.rename` looks the destination up first, then uses plain RENAME (OpenSSH's refuses any name in use but a dangling link; the lookup is for other servers); a change of case alone within one folder uses `posix-rename`, after the folder's listing shows no second file. `SFTPChannel.replace` is the temp-and-rename that does replace: with `posix-rename@openssh.com` it is atomic; without it the old file steps aside under a hidden name (`.transfer-old-<uuid>`) and comes back if the new one cannot take its place. The aside is recorded with the temps (`AsideLog`) until it is back or removed, so after a dropped connection the next login puts it back, or removes it when the new file took its place. Its record's owner is `<uuid> aside`, which 0.1.7 and 0.2.0 never select: 0.1.7 would read the record as a temp and remove the old file's only copy. A record 0.2.0 wrote under the server's own key moves to that owner each time the library opens, with no schema change, so 0.2.0 still opens it.
- Open in Terminal (`terminalCommand`) is offered only while logged in and joins the master; if the master has gone by the time the command runs, ssh logs in with the same port and identity, never as a master on Transfer's socket. A passenger does not set `Compression=no`: it rides the master's.

## Transfers

- **Files:** every direction writes a hidden temp beside the final name (`.<name>.transfer-<uuid>`, the name cut on a character boundary so the temp fits 255 bytes: `KeepBothName.temp`, sharing `LiveDecision.siblingName`) and renames it into place. Temps on both sides are recorded in SQLite before the first byte. A server's is forgotten only once removed, and one that could not be removed goes at the next login. The next launch unlinks each recorded Mac temp that is a file with a temp's name (`TransferHub.isTempName`; the library may be a copy naming any folder) and forgets every record. A download takes the server's permissions under the umask without setuid, setgid, or sticky bits, and is quarantined as a browser's download is, a Live working copy too (its type's default app may run it), except a Live copy of a Terminal script (`.command`, `.tool`: `EditableFile.quarantinesLiveCopy`), which Gatekeeper lets no app open, not even an editor; every Live copy lands 0600, so none runs; View and preview copies are read-only, so an editor never saves into one. Each data channel keeps 2 MB in flight, 32 requests of 64 KB. A short READ reply is not the end of the file: `ReadPlan` asks again for the rest (a file with no listed size reads through it until EOF), only EOF ends a download early, and a download that would leave a gap fails. A download reads only up to the listed size, so every channel checks the file it opened against the listing: the owning channel sends FSTAT with its first READs and, before writing a byte, fails a mismatch with `changedOnServer`, which retries like a dropped connection, so a file that grew is never placed cut short. A channel sends a file's requests without waiting where the server's in-order handling allows: an upload's writes, FSETSTAT (mode and time), and CLOSE go out together, as do a server copy's two OPENs and then its `copy-data`, FSETSTAT, and CLOSEs; the rename waits until every write and the close are acknowledged. A file of 8 MB or more also takes up to three more channels that are idle or can open then (`withSpareData`, never ahead of a waiting caller): each opens the file itself and takes 64 KB pieces from one `DownloadParts` or `UploadParts`; a helping download channel checks FSTAT first and steps aside on a mismatch; any piece failing fails the file and removes its temp.
- **Placement:** every name from a server that reaches the Mac goes through `LocalPlacement`, and what already holds a name is settled by `Placement.settle`, the same in every direction: nothing there writes, a folder merges into a folder, the same file (size and whole-second time) or the same link is skipped, a folder never replaces a file or the reverse, and anything else asks through `OperationPrompts.current`, the operation's own prompt, set by the model's operation runner. With nobody to ask the operation fails. A Replace removes only what the user was asked about: the name is looked up again just before (a file's just before its rename, on the channel that wrote it), and anything else there now fails the item; a link made where nothing was is made at the name itself, so it never replaces what took the name since. A folder copy walks on the walker and hands file bodies to the pool as names arrive (a download places a folder's files first and lists its subfolders ahead, up to `walkWidth` at once across every walk: one at a time, 2,000 files in ten folders spent 760 ms at 20 ms listing before their bytes), lists a destination folder once instead of looking up each name, keeps at most `CopyTally.jobLimit` (224) file jobs in flight, copies links as links, skips sockets, FIFOs, and devices, and goes on past an item that fails, naming every failure at the end.
- **Small files down** (`SSHConnection+Tar.swift`, the rules in Core's `TarStream.swift`): a folder download sends files of at most 32 KB (`TarBatching.fileLimit`) with a known size and time through the server's own `tar`, after the walk has settled each name exactly as above, once enough of them are to come (`TarBatchFill`). A folder listed ahead is counted before its first file is placed; the root, listed as it is walked, sends its first 112 small files over SFTP as names arrive (`sftpFirst`, one round of the pool) and counts the rest at the end of its listing. The download streams from the first folder whose small files, with those of the folders already listed ahead of it, reach 150 (`minimumFiles`); below that no stream starts and nothing waits, and once streaming it streams to its end. Its small files are then held in batches of 64 files or 1 MB, and four streams start (`TarBatching.streams`), each a passenger `ssh -S sock … -e none -- host <command>` whose command is the constant `tarCommandLine` (`echo TRANSFER-TAR-1; exec env COPYFILE_DISABLE=1 tar -cf - -P --no-recursion --null -T -`, run with `ssh -q`). A batch's names go NUL-separated down the least loaded stream's standard input, after the names before them, so a stream's start (about four round trips) is paid once per download; its temps (`.<name>.transfer-<uuid>` beside the settled name, as SFTP's) are recorded in one commit first. A reader thread per stream checks the marker, then reads the archive defensively (`TarFormat.parse`, `TarBatchPlan`): a header must have its checksum and ustar or GNU magic and octal fields; pax and GNU long-name headers are read only up to 64 KB, at most eight before an entry; an entry is written only when it is a regular file whose name is exactly the next expected path (`-P` keeps it whole, as both tars then store it), with the listed size and mtime. The plan and the stream forget each file once it is judged, and a stream takes no more batches after 20,000 files (`TarBatching.streamFiles`); another takes its place once it has ended. A link, a hard link, a device, a sparse file, or an entry of another size or time is skipped and that file goes over SFTP; a name never asked for, a broken header, or a cut stream ends the stream, and everything not landed goes over SFTP. A file is written only into its own temp, created `O_EXCL | O_NOFOLLOW`; a cut one is removed. Once a batch's entries are all judged, each file written is looked up again on the walker (one burst of LSTATs) and lands (`land`: quarantine, mode under the umask, time, rename as SFTP's) only when the server still lists it as it was, so a file changed or truncated while tar read it is fetched again; the rest goes over SFTP in the same job. The places: a stream is a session on the master like a data channel, so streams and the pool share the seven data places; once a download streams, the pool opens no channel into the streams' four (`keepTarPlaces`), and a stream that finds none free takes the next data channel to go idle ahead of the pool's own waiters. tar is probed once per login, as the first folder download starts: the command with no names must print the marker and an empty archive and exit 0, within 15 s and 64 KB; a server without `tar`, whose shell prints at startup, or whose tar refuses the flags gets SFTP for the login. A stream's standard error is read: tar reports a read error only there and pads the file with zeros (a file truncated or unreadable on the server), so anything past what the probe saw there (a shell's startup output) faults the stream. A faulted stream lands nothing more, its waiting batches go over SFTP, and every file it placed comes again over SFTP before the download ends: a stream keeps what it placed until it has closed clean, and one whose standard error is still open a second after its archive counts as faulted. A stream silent for 60 s while a batch waits on it (`tarStallLimit`) is stopped, and the batch's files not yet written go over SFTP. Cancel terminates the streams and removes every temp. GNU tar 1.35 and bsdtar 3.5.3 behave alike for all of it. Measured with the bench, SFTP alone against tar alternating run by run in one session, both tars: 2,000 small files in ten folders at 20 ms in 0.42 s (was 1.14 s), at 80 ms 0.93 s (3.7 s), with no latency 0.27 s (0.42 s); 500 of 16 KB at 20 ms 0.25 s (0.39 s); at 20 and 80 ms no case of 10 to 2,000 files, flat or in ten folders, was slower (worst 1.01x).
- **Pastes and moves** (`TransferEngine`, behind `SessionProvider.transfer`): on one server, a copy on the server (`copy-data`, else through the Mac), or a rename per item when moving (onto a name the folder already holds, the item is copied on the server with the collision asked, and moved as between servers); pasting into the items' own folder makes `name copy`. Between servers the two halves are pipelined (`across`, `Relay`). Each item is walked whole first, up to 16 items ahead along with a lookup of its name at the destination, and the copy takes only what that walk found, so a destination the source also reaches never feeds the copy its own output. No name of it reaches the Mac's disk (each file passes through a numbered scratch file), so names the Mac's disk could not hold apart or that are not UTF-8 go as the servers hold them; Finder staging still refuses them. One task then takes the items in order, settles each name at the destination (asking there about a collision, so questions now come while earlier files are still copying), and hands each file to a job that downloads it into a file of its own in a folder in `Scratch/` under the cache root, uploads that, and removes it once the upload's rename lands. At most `CopyTally.jobLimit` jobs run at once, and their files take at most 256 MB of scratch by listed size (`RelayLimits`); a file larger than that goes alone. An item that reaches a name an earlier item is still writing waits for that item, and Keep Both passes over names still in flight. An item is checked, and in a move its original removed, once all of its own jobs have ended. A retry settles each name before anything comes down, so what landed is neither downloaded nor uploaded again. Scratch temps are not recorded: the hub empties `Scratch/` at launch, under the library lock, so a crash leaves no copy behind (a server copy without `copy-data` passes through one too). A single file still goes down whole before it goes up: at 20 ms a 512 MB file takes 3.3 s, and overlapping its halves inside the file (uploading the download's contiguous prefix) would need the upload's reads to wait on the download and its rename on the download's checks, in the channel's send path every upload shares. The row counts each byte twice, down and up, against twice the total, so its speed is the two halves' sum and its time left stays right; each file and link counts once. A walk (`walkTree`, a move's check, the clipboard's count) lists up to eight folders at once on the walker channel (`walkWidth`). From this Mac, uploads. A move copies, walks the original again, and removes it only when `MoveCheck` finds this item wrote a complete copy keyed by exact name bytes: a file or link counts only where this item itself wrote it, so nothing else at the destination (what was there, a lookalike that arrived during the copy, an earlier item's copy of the same name) passes for it, and in a move a lookalike is asked about, never skipped. Between servers the removal takes only the verified entries still as they were, and a folder only once it is empty; what changed or was added since stays, and the item is reported as changed during the move (`TransferKept.Reason.changed`). A Live save under the original since the request began (`LiveSync.saveMark`, read before anything is copied) keeps all of it. Finder originals go to the Trash whole, which keeps anything added since where the user can find it. A move between saved servers, from the Mac, or onto a taken name on one server first makes a uniquely named folder at the destination and looks for it beside the originals, so two routes to one disk never copy an item onto itself; between servers or on one, a folder already at an item's name gets such a probe too, looked for under the item, which refuses the item when found (a bind mount or one share at two paths, whose parents differ); a paste of a folder from the Mac also looks for it inside that folder, so a server that reaches this Mac's disk never copies a folder into itself. A Live file with unsynced edits keeps its original. Every item gets its turn: one that fails is collected with the kept originals, and all are reported together once the rest are done (`TransferKept`); only a cancel, a dropped connection, or a timeout ends the paste at once. The request's memo, kept per item, holds what each attempt finished, the names Keep Both chose, and what each item wrote, so a retry does none of it twice and no item counts another's copy as its own.
- **Previews:** the cache lives in `Preview/` under the cache root, capped at 1 GB by last use and excluded from backup. A file keeps its remote name (Quick Look's Open With and a viewing app show it) inside a folder named for the SHA-256 of the server's id, the path's bytes, and, for a partial copy, the file's size and time, so two servers never share an entry and an unchanged file reuses its copy; eviction takes whole folders. The inspector fetches only the first 64 KB of a text file (`EditableFile.previewHead`); Quick Look renders the first 512 KB of one as highlighted HTML; everything else is fetched whole and reused while its size and time match. The inspector previews other files only up to 10 MB (`InspectorPreviewPlan.limit`, which `SSHConnection.inspectorLimit` shares), and only types it can show (`InspectorPreviewPlan`: pictures, and what Quick Look draws as more than an icon); it fetches nothing for any other file, and prefetches the neighbors of each preview one at a time under the same plan. The limit is checked against a fresh stat too, and a file listed without a size is refused. View → Clear Preview Cache is `SessionProvider.clearPreviewCache`, which the hub answers from `Store.previewCache`, so it works in a window with no server.
- **Opening a copy:** a viewed or Live copy goes to its type's default app through `FileOpener` (`WindowSupport.swift`), which asks once for an app when the type has none and sets it as Finder's Always Open With does, unless the app is a runner (`FileOpener.runs`), which Finder would then run such files in. The user opens a file to read or edit it, so when that app would run it (`FileOpener.runners`: Terminal, iTerm2, Ghostty, Python Launcher, Jar Launcher), `FileOpener.editor(replacing:plainText:)` picks the default app for `public.plain-text` instead, or TextEdit when that is a runner too.

## The clipboard

`Clipboard.shared` (`Clipboard.swift`) is one per app and mirrors the general pasteboard. Command-C writes the remote paths (`remoteDragType`, `com.github.shreeve.transfer.remote-items`, plus the paths as text), counts the tree on the walker, and downloads the items to a staging folder so Finder can paste them, adding the file URLs when the download is complete: Finder reads only file URLs from the clipboard. Copies over 1 GB, trees that could not be counted in full, and trees holding two names the Mac's disk cannot tell apart are not staged. Clips stage under `Staging/` in the cache root, which a launch empties: only one copy of Transfer runs on a library, and each library has its own cache root. A replaced clip's folder is removed ten minutes later, since Finder may still be pasting from it; quitting removes `Staging/`. Escape on a clip from Finder hides the bar and leaves the pasteboard alone. Paste and drop (`PasteActions.swift`) only queue a `TransferRequest`.

## Live files

Live files are one component, `LiveSync` (`LiveSync.swift`), owned by the hub: the records and their `live_files` rows (dirty, paused, the conflict and what the server held, the working copy's exact stamp and SHA-256 at the last sync), one FSEvents stream over the Live folder (`LiveWatcher`), and one worker per server. Every pass and every command for a server's files (open, conflict choices, discard and stop, and a rename or delete under a Live path) runs on that worker in turn, so nothing races and nothing is locked; Pause's flag is the one write from outside. A rename or delete also waits for a Live open under that path still queued or downloading. A removal above a Live file with unsynced bytes refuses with `liveUnsynced` unless forced, and a forced one discards the Live files only after the server's delete succeeds. Delete forces an item only when every unsynced Live file under it is one its sheet named (`deleteSelection(warned:)`); an item holding one the sheet did not name is refused, and the sheet comes back naming it. Remove Server's check, the close, and the removal of `Live/<id>` happen in one actor turn (`closeIfSynced`), after a last count that reads no bytes, so no save lands between them. A record's working copy is always `Live/<connection>/<id>/` plus the stored file name through `LocalPlacement.child`: the stored `local_path` supplies only the name (it is still written, for older Transfers), so a moved library keeps its copies and a row naming another place never reaches outside `Live/`. `LiveDecision.isUnsynced` is the one test for "holds bytes the server lacks", counting an edit no pass has seen yet; Stop, Remove Server, Delete's warning, and Quit all use it. Stop Live Editing is `SessionProvider.stopLive` → `LiveSync.stop`, library-wide by `LiveFileID`: `LiveDecision.stopPlan` asks first whenever an unsynced file of the batch is not in `warned` (nothing stops, the unsynced ones come back for the sheet, so Cancel keeps all), else each server's files stop on its worker, between passes, each checked again there, so one edited after the question stays and comes back; a stop needs no login. It drops the record and working copy as Discard did (`drop`). The hub's `libraryLiveFiles` (every server's files, named by server) and `liveChanges` (one stream per window, fed by every `.liveChanged` and every open or close, whether or not that server is logged in) feed the toolbar badge.

A rename changes only the remote path: the working copy keeps its old local name, because an editor holding it open keeps saving there and the watcher knows the copy only by that name. A pass acts only on a working copy that has held still for 350 ms, then asks `LiveDecision` what to do, feeding it a digest when the stamp moved and the server's file when the copy changed: a touched-only copy is restamped, not uploaded; a watcher event that finds the stamp unmoved is an echo and does nothing; a missing copy gets a second look a second later; an unreachable server parks the pass until login; other failures retry at 1, 2, and 4 s. An upload requires the stamp the pass saw hold still, reads through `NSFileCoordinator` without asking an editor to save (`.withoutChanges`: an NSDocument editor asked would save text the user has not saved), goes on the interactive lane, and checks just before the rename that the server still holds the base; the new base is our own temp's fingerprint. A server file with the edit's size and time is adopted as synced only when it is our own unconfirmed upload. The temp takes the server file's permissions, never the working copy's private 0600. A conflict writes the `(server)` copy first, then sets the flag and sends the event; that name, and the refresh download's, are cut to fit 255 bytes (`LiveDecision.siblingName`). Keep Local and Keep Both first wait until the working copy has held still for 350 ms and refuse while it is still being written; Keep Local expects the server file seen when the conflict was raised. Keep Remote on a file that has left the server since raises the conflict again as removed, keeping both copies; the record goes only when the conflict answered already showed no file (`LiveDecision.keepRemoteForgets`) or Keep Both uploaded the copy first. Server bytes replace a working copy only through one helper: downloaded beside it, measured there, and renamed over it in a coordinated write, only if the copy still has the expected stamp, so an editor's save is never overwritten. A copy holding no edits, touched or not, is refreshed only when the user opens it again (`LiveDecision.refreshesOnOpen`). If FSEvents cannot watch the Live folder, every copy is stamped every 2 s and the user is told. A synced copy idle for a day is forgotten at launch. `SSHConnection` is the `LiveServer` (look up, fetch, save with an expectation, list names, check, emit). Compare opens `opendiff`.

While a server is logged in, `LiveSync` checks its files on a timer (`startChecking`, started by `connected`, stopped by `disconnected` and `close`): the first round `checkInterval / 12` after login (5 s), then every `checkInterval` (60 s), each wait jittered by a tenth; tests shorten it with `checkRemote(every:)`. A round runs off the worker, so no pass or command waits on it, and skips every file with a pass due, running, or waiting for the server, an upload in flight, or a conflict. It is one `liveCheck` per file, a stat on the walker channel and never a download: browse and interactive carry what the user waits on, and a data channel can queue behind a copy; a walk is background work one stat a minute does not slow, and when the walker is down the round ends until the next. What a round found goes to the worker as one command, which ignores a file whose state moved since its stat and asks `LiveDecision.afterCheck`: the base clears the flag; our own unconfirmed upload (`pending`) is left to the next pass; anything else sets `Entry.remote` (the conflict kind it would raise), memory only, so it is found again by the first round after a login, and the first flag of a file emits one notice. A copy holding edits the server lacks (a seen or unseen edit) gets the conflict at once instead, through `raiseConflict`, unless paused. A flag never writes the working copy or uploads; `recordSync` (a save, an adoption, a refresh on open, Keep Remote or Both) and `raiseConflict` clear it, and it goes with its record. `LiveFile.serverChange` carries it to the window, whose status puts it right after a conflict.

## The library

`Store` (`Store.swift`) keeps `transfer.sqlite`: saved servers, stars (table `pins`), Live records, and remote temps. `PRAGMA user_version` is the schema version, and opening migrates one step per transaction, re-reading the version under the lock: 1 is the schema of 0.1.0 to 0.1.7, which kept no version; 2 drops the write-only `recents` table; 3 marks the move to exact-byte paths and changes no row; 4 changes no row either and gives the library's `config.json` each entry of 2.0.0's new source types (`TransferConfig.addedIn2`) its list lacks, appended after the user's own, which keep their order (`TransferConfig.adding`, `ConfigLoader.add`). Being a schema step, it runs once, so an entry the user removes later stays removed; a missing `config.json` is left for the first load to write (the built-in list has them all), an unreadable one for the load to keep aside, and a failed write is logged, never fatal. 0.2.0 to 0.3.1 refuse a schema-4 library as newer; 0.1.7 keeps no version and still opens it. A path is stored as text when its bytes are UTF-8 without a NUL, as every older Transfer wrote it, and as a blob otherwise (`StoredPath`); reads and matches compare `CAST(path AS BLOB)`, so either class is the same path. After a downgrade 0.1.7 still opens the library, and its text matches (Unstar, temp cleanup) find every row it could have written. A library newer than the build is refused, untouched, and the app says why and quits. The file is in WAL mode (hence `transfer.sqlite-wal` and `-shm` beside it) with `synchronous = FULL`, so a committed Live record survives a power loss, and a 5 s busy timeout for an older Transfer, which takes no lock. Saved servers are read in Finder's order (`localizedStandardCompare`), and a row whose id is not a UUID is skipped. `config.json` is written with the built-in defaults (`TransferConfig.builtIn`) on first launch; an unreadable one is kept as `config.json.bak` before the defaults take over.

## Still open

- Small files stream down with `tar` only in folder downloads, measured against the local sshd with the delay proxy, with bsdtar and with GNU tar (`TRANSFER_TEST_TAR=gnu`), not yet against a remote Linux server. With no latency, a single flat folder of about 113 to 250 small files runs up to 12% slower than SFTP alone (150 files: 35.0 against 31.3 ms): its files past the first 112 wait for the end of its listing to be counted. At 20 and 80 ms nothing measured is slower. Pastes between servers keep SFTP for their download half: their relay is bound by the upload half (2,000 small files: 1.24 s up alone, 1.67 s across), and since bsdtar holds names until more come or its input ends, a relay that waits for each file needs a stream per batch, which measured slower (1.88 s). Uploads stay on SFTP: `tar -x` on the server would need its staging folder in the command line or a server-side extraction we do not control (modes, links, what it overwrites), and each file would still cost an SFTP rename.
- Left from the round-2 audit on purpose (useful, but not small or not proven): `TransferModel` could shrink by about a third by merging its three sheet queues into one, letting `ServerContext` own each server's listings, stars, and Live rows, and moving the shelf and the listing cache out (the cache into Core, with tests); the data pool could be one `dispatch()`; symlink targets still pass through `String`, so a target that is not UTF-8 is not kept byte for byte (`SFTPChannel.readlink`/`symlink`, `TreeEntry.link`, `RemoteSession.readlink`); an orphaned master from a crash is ended only when that server is next used; a known-hosts path holding a space is not read; Open in Terminal's fallback login still passes `Compression=no` (`ServerTests` pins it).
- There is no CI: the macOS 27 SDK is not available there, and the UI is checked by hand.
- Seen in the round-2 E2E, not fixed: during a login to another server the title's path and the sidebar highlight still show the previous server; the server sheet keeps the mouse from the sidebar; a control character in a name does not show in the title or path; Quick Look of highlighted text offers "Open with" the default browser, since the preview is an HTML file; and a Live upload's snapshot (`LiveSync`, `live-<UUID>`) is taken in `$TMPDIR`, which the system may purge, rather than in the library. From the confirming pass: in column view a drag begun in a background window still brings that window to the front on the drop (the browser's tables are AppKit's own, so they cannot delay ordering as the icon and list views do); and the clipboard bar keeps a server's name from when the items were copied, so a rename shows the old one.

## Traps

- bsdtar reads its `-T` list with `fread`, which waits until its buffer fills or the input ends, and it writes its archive in 10 KB records: a stream's last names, and its last entries, come only when more names follow or its input closes. A folder download keeps feeding its streams and closes them once its walk ends; a caller that waits for a batch before it sends the next deadlocks, as a paste between servers did. A Mac's bsdtar also adds `._` AppleDouble entries unless `COPYFILE_DISABLE=1`, and both tars store `/a/b` as `a/b`. Measured on macOS 27's bsdtar 3.5.3.
- A tar stream is an ssh session like an SFTP passenger, so it counts against sshd's `MaxSessions` (10: three reserved, seven data). The pool spreads small files over every idle channel, so once a folder's first files had opened all seven, no stream found a place and every batch fell back to SFTP; hence the places kept once a download streams and the idle channel handed to a waiting stream. Keeping them from the first small file instead held every download with small files, streaming or not, to three channels.
- A walk whose listings read ahead are already in never suspends, so it held the session actor until its end and the streams' starts, queued on it, waited behind it (a tree of 300 at 20 ms: 445 ms, against 300 over SFTP). The walk yields once per folder while it streams. Holding a folder's small files for a second pass, even with its listing in hand, cost 5 to 7 ms on 100 files at 20 ms and 5 ms on 150 with no latency, for reasons the bench did not show; a folder listed ahead is therefore counted up front and placed in listing order, and only the walked root holds files, past its first 112.
